# Engineering audit — why the corpus stalled at a few hundred citations, and what was changed

Date: 22 September 2026. Scope: every file under `scraper/`, `migrations/`, `cloud/`, `docker-compose*.yml`,
`.env.example`, the GitHub workflows and the test suite, read line by line, with the git history of the
PakistanLawSite path (#59, #60, #61, #66, #69, #76, #79, #81, #86, #92, #95, #98, #101, #104) reconstructed
to see what each amendment changed and what it left behind.

The short version: the harvesting code was, by 21 September, mostly able to read the live CitationSearch
grid correctly. What kept the corpus at roughly 450 citations was not one bug but a chain of eight
independent throttles and stalls, each added or left in place by a different amendment, sitting between
"a page was read" and "a judgment appears in the corpus". Any one of them alone caps the corpus at a few
hundred rows a day; together they explain the number exactly. Every one of them is fixed in this change
set, and each fix carries a regression test.

---

## 1. Findings, in order of impact

Severity: **S1** = stops or throttles the whole corpus; **S2** = loses a large slice of the data or the
session; **S3** = wastes time or hides a failure.

### F1 (S1) — The service silently flips itself from backfill to updates mode within one minute of boot

`scraper/harvest_mode.py::backfill_progress` declared backfill "complete" when the crawl frontier had no
pending rows and the (optional) targets were met. Both targets default to 0, which counted as "met".
The frontier is empty at first boot (no source has run yet), and the PakistanLawSite citation grid never
uses the frontier at all. `dispatch_due_sources` runs every 60 seconds and, with `HARVEST_AUTO_SWITCH=true`
(the `.env.example` default), switched the mode to **updates** on its first tick.

Effect: everything then ran on the updates cadence: PakistanLawSite once every **6 hours**, with the
updates pacing profile (4–9 s between pages, 300 pages/hour), and every public source once every 6 hours
with a 40-document limit. Anyone who set backfill from the dashboard saw it revert within a minute
whenever the frontier happened to be empty.

Fix: auto-switch requires a configured target (`BACKFILL_TARGET_JUDGMENTS` and/or
`BACKFILL_TARGET_STATUTES` > 0) that is actually reached, plus a drained frontier. With both targets at 0
the mode never changes on its own; the dashboard's `/admin/sources/harvest-mode` now reports
`auto_switch_blocked_reason`. Tests: `test_backfill_progress_never_completes_without_configured_targets`,
`test_dispatch_does_not_auto_switch_to_updates_on_empty_frontier`.

### F2 (S1) — One grid window per job, then idle; and the per-window cap on the server was 40

`run_citation_grid_surface` read **one** window of the grid (at most `PLS_ARCHIVED_GRID_MAX_ROWS` = 200
rows), fetched at most `PLS_CITATION_GRID_MAX_DETAIL` detail pages, and returned. The job then ended and
the source waited for its next Beat kick (15 min in backfill, 6 h in updates). `.env.example`, which the
cloud installer copies verbatim into the server's `.env`, still said `PLS_CITATION_GRID_MAX_DETAIL=40`
(#76 introduced 40; #98 raised the code default to 120 but not the file). `BACKFILL_PLS_CITATION_GRID_MAX_DETAIL`
existed in `config.py` and `.env` but was never read by the pipeline.

Arithmetic for the deployed server: F1 put it in updates mode, so 4 jobs a day × 40 details = **160
downloads a day at most**; over the days since #76 that is the ~450 figure, before any losses below.

Fix: the connector now runs windows back to back inside one job for `BACKFILL_PLS_RUN_MAX_MINUTES`
(50) in backfill mode, honours `BACKFILL_PLS_CITATION_GRID_MAX_DETAIL` (300 per window) in backfill and
`PLS_CITATION_GRID_MAX_DETAIL` (120) in updates, commits progress after every row as before, stops
cleanly on a wrap of the grid, a pacing budget, a slot loss or a block, and reuses the page rendered for
the search map instead of loading the 10–16 MB grid twice per job. `.env.example` now carries the real
values. Test: `test_pipeline_citation_grid_backfill_run_takes_consecutive_windows`.

### F3 (S1) — Promotion starved itself: old quarantined rows filled every batch

`promote_staging_records` selected staging rows with `status IN ('extracted','quarantined') AND
promoted_to_id IS NULL`, ordered by `created_at`, limit 200, every 15 minutes. A quarantined row keeps
`status='quarantined'` and `promoted_to_id=NULL` forever (its review-queue entry is created once and it is
then skipped). PakistanLawSite produces many quarantines (headnote-only pages, login stubs, low
confidence). Once 200 quarantined rows older than the newest extracted rows existed, **every batch
consisted only of rows that were skipped**, and newly extracted judgments were never promoted again,
while harvesting continued and the dashboard showed rows being staged.

Fix: extracted rows and quarantined-without-queue-entry rows are selected in two separate queries (the
second with `NOT EXISTS`), so promotion can never be crowded out. The Beat schedule promotes 500 rows every
5 minutes, and the maintenance queue has its own worker (F7). Test:
`test_promote_staging_records_is_not_starved_by_old_quarantined_rows`.

### F4 (S2) — Reporter shards dropped every non-PLD citation

With `BACKFILL_LOGIN_SESSION_CONCURRENCY=2` (the default), the dispatcher enqueued two "reporter shard"
jobs. `reporter_from_citation` only recognised a reporter at the **start** of the citation string
("PLD 2024 SC 1"). Every other reporter is cited year-first ("2024 SCMR 1", "2024 CLC 1234", "2024 YLR 5",
"2024 P Cr. L J 12"), so the function returned the year, neither shard claimed the row, and it was counted
as `reporter_skips`. In sharded runs only PLD rows were ever downloaded. Rows for reporters not in
`PLS_SUBSCRIBED_REPORTERS` (PTD, CLD, GBLR, PLJ, NLR, KLR …) were dropped by both shards too.

Fix: the reporter is found anywhere in the normalised citation; shard 1 takes its listed reporters and
shard 0 is the catch-all for everything else, so every row of the grid belongs to exactly one shard.
Tests: `test_reporter_from_citation_handles_year_first_reporters`,
`test_pipeline_citation_grid_shard0_is_catch_all_and_shard1_takes_its_reporters`.

### F5 (S2) — Two shards on one login: the site logs one of them out

Each shard prefers slot N+1, but when its slot was not ACTIVE it fell back to "the current slot", i.e. the
other shard's slot. With one human login (slot 1 only, the normal case) both shards opened Chromium on
the same cookies at the same time. PakistanLawSite allows one login per account; the second browser
ends the first session ("Logout From All Devices"), the connector sees a login page, marks the slot
`NEEDS_HUMAN_LOGIN`, pauses the source and notifies. That is the recurring "one issue or the other"
that needed a fresh human login.

Fix: the dispatcher enqueues two shards only when **both** slots are ACTIVE and otherwise one unsharded
job; a shard whose own slot is not ACTIVE returns `skipped=shard_slot_not_active` without touching the
other slot; the continuity runner never fails a shard over to the other shard's slot. Tests:
`test_dispatch_due_sources_runs_one_unsharded_job_when_only_one_slot_is_active`,
`test_pipeline_shard_never_borrows_the_other_shards_slot`.

### F6 (S2) — Ordinary words inside a judgment HALTED the source or expired the slot

`security.classify_response` scanned the **entire** page text for phrases such as "access denied",
"unusual activity", "suspicious activity", "verification code", "one-time password", "please log in".
It was written for short notice pages, but the same function classifies every 50–300 KB judgment page.
A criminal or banking judgment containing any of those phrases produced `ExplicitBlock` (source
**HALTED**, slot HALTED, admin review required) or `VerificationRequired` / `LoginRequired` (slot
`NEEDS_HUMAN_LOGIN`, source PAUSED). Nothing was bypassed and nothing was lost, but the harvest stopped
until a human intervened, and the halting page was never retried.

Fix: a page that is a document body (≥ 60 000 characters, or carrying a "Citation Name:" label) is
classified by HTTP status and URL only; a page that offers a Logout link is treated as authenticated
(the "Update Subscriber" modal on case pages contains password fields, which previously matched the
login markers). Short notice pages classify exactly as before; HTTP 403/429/451 still HALT. Tests:
`test_classify_response_ignores_block_and_login_phrases_inside_a_judgment_body`,
`test_classify_response_authenticated_case_page_with_password_modal_is_ok`.

### F7 (S1/S3) — Dispatch and promotion ran on the same worker as the public scrapes

`worker-public` served the `scraper` **and** `maintenance` queues with two processes. Two long public
runs (PakistanCode drains 200 documents per run, with OCR) occupied both, and `dispatch_due_sources`
(the scheduler itself) and `promote_staging_records` waited behind them for as long as those runs
took. PakistanLawSite kicks and promotions were therefore late or missed for hours at a time.

Fix: a `worker-maintenance` service serves the `maintenance` queue; `worker-public` serves `scraper`
only (`docker-compose.yml`, `.cursor/environment.json`). The compose file adds the service on the next
`docker compose up -d --build`.

### F8 (S3) — A restarted worker blocked its source for three hours

`run_source` skips a source that already has a job with `status='running'`, and only retires such a
row when it is older than three hours. Every deploy recreates the worker containers, so every one of
the ~20 deploys since 19 September left a "running" PakistanLawSite job that blocked the source for up
to three hours, with the log line "already has running job; skipping duplicate kick".

Fix: the connector heartbeats its `scraper_jobs` row (`updated_at`, live counters) on every page it
charges and every committed row; the dispatcher retires a running job that has not heartbeated for 30
minutes. Tests: `test_run_source_retires_running_job_without_heartbeat`,
`test_run_source_keeps_running_job_with_recent_heartbeat`.

### F9 (S3) — Pacing and continuity exceptions in the grid path were reported as job failures

In the frontier (form) path these exceptions were caught and recorded as `paused` / `pacing_paused` /
`halted`; in the citation-grid path they propagated, so `scraper_jobs.status='failed'` and
`scraper_sources.last_error` showed "PAGES_PER_HOUR=300 spent for …" or "disconnected: …" as if the run
had crashed. Progress was safe (committed per row), but the dashboard reported failures that were
normal pauses. Fixed: the grid path records the same flags and returns cleanly
(`test_pipeline_citation_grid_pacing_budget_ends_run_cleanly`). Real programming errors still propagate
and fail the job, as the existing crash-recovery test requires.

### F10 (S3) — Wrap-around re-downloaded every quarantined or not-yet-promoted page

The "known citation" skip (#95) looked only at promoted judgments. Pages staged but not yet promoted
(promotion lags by minutes), and pages quarantined for review (headnote-only, login stub, low
confidence), were downloaded again on every pass of the grid. With ~20 000 rows and a meaningful
quarantine rate this is thousands of wasted detail fetches per pass. Fixed: rows whose citation already
has a staging row (`extracted`, `promoted`, `duplicate`, `quarantined`) are skipped and counted as
`staged_citation_skips`; `PLS_CITATION_GRID_SKIP_STAGED=false` restores the old behaviour if a re-read is
ever wanted. Test: `test_pipeline_citation_grid_skips_rows_already_staged`.

### F11 (S3) — The "Case Description" control was read before the page had rendered it

`_capture_case_description_modal` looked for the control once, immediately after `domcontentloaded`. On
a `ReferenceCaseLawSearch` page whose scripts render the control a moment later, the page was classified
`headnote` / `case_description_selector_missing`, staged, and quarantined at promotion, and (after F10)
never re-read. Fixed: the capture waits up to `PLS_CASE_DESCRIPTION_WAIT_SECONDS` (6) for the control.

### F12 (S3) — The grid page was rendered twice per job and measured with `innerText`

`ensure_search_map` navigated to CitationSearch and took a compact snapshot from row 0 (never used);
`run_citation_grid_surface` then navigated again at the cursor. `_dom_shape` built its preview from
`document.body.innerText`, which forces style and layout of the whole 20 000-row table on every call.
Fixed: one navigation per job (the map's page is reused when its start row matches the cursor); on the
grid page the preview is built from the chrome around the table with `textContent`. A snapshot that
times out is retried once with half the window before the browser is treated as disconnected, instead
of reconnecting and re-rendering the whole grid only to time out again.

### F13 (S3) — When the cursor could not be honoured, the run re-read the first window forever, silently

If neither `dom_absolute` nor `datatable` seek confirmed the requested row, the window fell back to
row 0 and the cursor was set to 0 + rows processed: on a grid where the seek fails, the job re-reads the
same first window on every run, counts every row as a duplicate and reports success. This was the
condition #86, #101 and #104 were chasing. The seek itself is unchanged (it is correct for the live
grid, which holds every row in the DOM); the pipeline now raises one `PLS_GRID_SEEK_UNCONFIRMED`
notification, records `citation_grid_cursor_unconfirmed` in the job stats, and ends the multi-window loop
after such a window so the budget is not burned on the same rows.

### F14 (S3) — The Redis client opened for the login-session lock was never closed

One `redis.asyncio` client per job leaked. Fixed: the lock closes the client it created.

## 2. What the earlier amendments did, and what each left behind

| PR | What it did | What it left in place |
|---|---|---|
| #59 backfill mode, dashboard controls | Added the two pacing profiles, the mode switch and auto-switch | Auto-switch with no target (F1); public + maintenance on one worker (F7) |
| #60 saved credentials, #61 auth gating | Encrypted per-slot credentials, timeouts | — |
| #66 oversize guard, #69 read-button path | Stopped `page.content()` on the 16 MB grid; synthesised `ReferenceCaseLawSearch` detail URLs | Two grid renders per job (F12) |
| #76 compact harvest + detail cap 40 | Bounded a run that "hung for hours" | The cap itself (F2); `.env.example` never updated |
| #79, #81 durable cursor + per-row commits | Progress survives a restart | Job row not heartbeated (F8) |
| #86, #101, #104 absolute seek (DataTables, then DOM slice) | Cursor can move past the first 200 rows | Silent fallback to row 0 when the seek is unconfirmed (F13) |
| #92 `/login/check` stub fix | Real case pages parked on `/login/check` are no longer stubs | Block/login phrase scan over whole judgment bodies (F6) |
| #95 skip known rows, #98 cap 120 + reporter shards | Faster passes over known rows; two shards | Reporter detection only at string start (F4); shard slot borrowing (F5); staged rows re-read (F10); grid-path exceptions uncaught (F9) |
| #99, #100, #105 stub / chrome guards | Fail-closed promotion rules | Promotion batch starvation (F3) was pre-existing and became visible once quarantines accumulated |

None of these amendments was wrong in what it set out to do; each fixed the symptom in front of it and
did not model the end-to-end throughput. The corpus is bounded by the *minimum* of: grid windows per
day × details per window (F2), promotion capacity per day (F3, F7), the fraction of rows a shard claims
(F4), the fraction of time a slot is ACTIVE (F5, F6), and the fraction of time the source is not blocked by
a stale job (F8). Each of those factors was independently at or near zero at some point in the last week.

## 3. Throughput after this change (what to expect)

Assumptions: backfill mode, one ACTIVE slot, `BACKFILL_LOGIN_DELAY 0.4–1.0 s`, a detail page taking
2–4 s to load and read, a grid window of 400 rows taking 10–20 s to render.

| Stage | Before | After |
|---|---|---|
| Detail pages per job | ≤ 40 (server `.env`) / 120 (code) | up to 300 per window, windows back to back for 50 min |
| Jobs per day | 4 (updates mode, F1) | continuous: a new job starts at the next Beat tick after the previous one ends |
| Detail pages per hour, one slot | ≈ 7 | ≈ 600–900 (bounded by page load time, not by the connector) |
| Promotion | ≤ 200 rows / 15 min, starving (F3) | 500 rows / 5 min on a dedicated worker |
| Two slots | both on one login, one logged out (F5) | each shard on its own slot, disjoint reporters, catch-all shard 0 |

A full pass over a 20 000-row grid is therefore a matter of one to two days of wall-clock time per slot,
not months. The pacing budgets still apply (`BACKFILL_PAGES_PER_HOUR=10000`, `PAGES_PER_HOUR=300` in
updates mode) and the contract's continuity and no-bypass rules are untouched.

## 4. What to do on the server (operator checklist)

1. **Deploy this branch** (re-run the *deploy-cloud* workflow or the installer). The compose file adds
   the `worker-maintenance` service and rebuilds the image.
2. **Edit `/opt/ssa-scraper/.env`** (the installer keeps the existing file, so the old values stay until
   changed). Set or add:
   ```
   HARVEST_MODE=backfill
   PLS_ARCHIVED_GRID_MAX_ROWS=400
   PLS_CITATION_GRID_MAX_DETAIL=120
   BACKFILL_PLS_CITATION_GRID_MAX_DETAIL=300
   BACKFILL_PLS_CITATION_GRID_SCAN_WINDOW=600
   BACKFILL_PLS_RUN_MAX_MINUTES=50
   PLS_CITATION_GRID_SKIP_STAGED=true
   PLS_CASE_DESCRIPTION_WAIT_SECONDS=6
   ```
   then `cd /opt/ssa-scraper && docker compose up -d`.
3. **Dashboard → Overview → Harvest mode → backfill.** It no longer flips back on its own.
4. **Human login**: slot 1 must be ACTIVE. Fill slot 2 only with a *second* account (or leave it EMPTY);
   the dispatcher runs one job with one slot and two shards only with two.
5. **Check after one hour** (`/admin/sources/PakistanLawSite/status`, `/admin/corpus/summary`):
   `citation_grid_progress.citation_grid_cursor.row_offset` advancing by hundreds; `scraper_staging_by_status`
   showing `promoted` growing every 5 minutes; no `SOURCE_HALTED` / `NEEDS_HUMAN_LOGIN` notifications.
6. **Review queue**: rows quarantined before this change as `login_stub` or `headnote_only` because of
   F11 are not re-read automatically (F10). To re-read them once: set `PLS_CITATION_GRID_SKIP_STAGED=false`
   for one full pass, then set it back to `true`.
7. **Server size**: one Chromium on the 16 MB grid needs ~1 GB; with two slots use the 4 vCPU / 8 GB
   droplet. Disk: raw HTML and text of every page are preserved (by contract); budget ~250 KB per
   judgment in Postgres plus the raw file.

## 5. What not to do

- Do not raise `BACKFILL_LOGIN_SESSION_CONCURRENCY` past 2, and never put two shards on one account: the
  site allows one login per account and ends the other session. That is the contract, not a limitation
  of the code.
- Do not lower `PLS_ARCHIVED_GRID_SNAPSHOT_TIMEOUT_SECONDS` below 15 s: a timed-out snapshot now halves
  the window and retries, but a very short timeout will halve it down to 50 rows and slow the pass.
- Do not set `HARVEST_AUTO_SWITCH=true` with targets you do not mean: with a target set and reached, the
  service goes to the 6-hour cadence and stays there until switched from the dashboard.
- Do not re-enable a HALTED source without reading the notification: HTTP 403/429 blocks are real and
  the contract forbids evasion. Phrase-based false HALTs from judgment text (F6) no longer occur.
- Do not edit `scraper/auth/archived_grid_seek.js` to "fix" a cursor that will not move: first read the
  `PLS_GRID_SEEK_UNCONFIRMED` notification and the job stats (`citation_grid_seek_mode`,
  `citation_grid_rows_seen`, `citation_grid_cursor_unconfirmed`); the seek is correct for the live grid.

## 6. Things reviewed and left as they are (with the reason)

- The four-tier search-form path (`run_tier1`, `run_paged_query`) is unused on the live site (the
  authenticated CitationSearch page is a grid, not a form) but is left intact for a surface change.
- The raw-first rule (preserve → provenance → staging → extract → promote) and every privacy guard
  (managed ScrapeGraph refused for login-session material, no stealth, no proxy, no CAPTCHA solving,
  HALT on explicit block) are unchanged and the guard scan still passes.
- `record_provenance` de-duplicates on the SHA-256 of the raw HTML. PakistanLawSite pages carry
  per-request tokens, so the same judgment fetched twice has two provenance rows and de-duplicates at
  promotion by citation and by full-text hash. That is correct under the contract; F10 removes the wasted
  second fetch.
- A PDF download answered with HTTP 403 still HALTs the source. Grid rows carry no PDF links today, so
  this path is not exercised; it is flagged here because a single unlicensed PDF would otherwise stop
  the whole source and should be reviewed against the contract before it ever matters.
- `crawl_max_pages` for public sources (40–200 per run) is a deliberate courtesy limit; with the
  scheduler no longer starved (F7) and the mode no longer flipping (F1) public sources run every 15
  minutes in backfill and drain on their own.

## 8. Post-deploy observation and follow-up (22 September, 21:15 UTC)

Three hours after deployment the harvest had promoted about 2,000 judgments and the grid cursor
stood at row 4,836 of 20,568. The login was lost at 17:27, at about 18:20, at about 19:20 and at
21:09 UTC (slot 1 `LoginRequired: login surface URL`, source PAUSED, human re-login each time).
Roughly hourly, without anyone else using the account, this is a session-lifetime effect, and one
half of it is ours: every job opened a fresh browser context from the storage state captured at
the human login and never stored the cookies the site renewed during the run, so consecutive
50-minute jobs kept re-presenting login-time cookies.

**F15 — live session state was never written back to the slot.** Fixed: after every citation-grid
window and at the end of every job the connector exports the browser's current storage state and,
when it differs, stores it in the same slot (`SessionManager.refresh_storage_state`; still the human's
login, only its live continuation). The slot's cookie names and expiry times (never values) are
logged when a slot is opened and when it is refreshed, and `LoginRequired` now names the URL the
site landed on, so the next loss can be traced to a specific expired cookie. No automated login is
added: a lost session still requires the human login the contract prescribes, and the
"Login with saved credentials" control on the dashboard is the one-click way to do it.

## 9. Second observation after the F15 deploy (22 September, 23:20 UTC)

The F15 build went live at 22:15 UTC; the human login was re-established at 23:01 and the harvest
resumed at 23:02 (first window of 300 details in 10.5 minutes, cursor 4,879 → 5,179, promotion
running again). The slot-open line settles one question: the site issues exactly two cookies, an
`ASP.NET_SessionId` and a `__RequestVerificationToken`, both session-scoped and both unchanged
across the run. The login is therefore tracked in the site's server-side session, not in a cookie
the site renews, so F15 is harmless but cannot by itself prevent the hourly loss (the write-back
finds the state unchanged and stores nothing).

The recorded loss reason, `login surface URL`, is produced only when the browser's final URL is the
site's public login page (`/Login/MainPage`, `/Login/Login` or `/Login/Index`); it is a genuine
redirect by the site, not a misread judgment page. Nothing on our side ends the server session:
the browser is closed without a logout, the pipeline opens exactly one browser per slot, and the
login-session worker runs one process. The two explanations left are both site-side: a fixed
session lifetime enforced on the server, or the site's single-session-per-subscription rule ending
the headless session whenever the same account logs in elsewhere (the connector already knows this
rule; see the `MULTILOGIN` markers). The interval between the 23:01 login and the next loss, now
recorded with the landing URL, decides between them; the operator can also confirm whether the
account was used in another browser at 17:27, 18:20, 19:20 or 21:09 UTC.

**F16 — concurrency target was not capped by the number of logins.** The backfill profile targets
two login-session workers, and both the dispatcher's running-job check and the Redis session lock
admitted a second job even when only one slot held a human login. With the worker at one process
this only queued idle jobs, but any operator raising `LOGIN_SESSION_CONCURRENCY` to 2 with a single
slot would have put two browsers on one login, which the site ends. The effective concurrency is
now `min(profile target, ACTIVE slots)` in the dispatcher and in the connector's lock.

## 10. The login loss measured (23 September, 00:30 UTC)

With the landing URL and the slot's login time now in the logs, two clean measurements exist:

| Human login (UTC) | Harvest started | Login ended | Pages fetched | Pace |
|---|---|---|---|---|
| 23:01:15 | 23:02:50 | 23:28:20 | 532 | 0.4-1.0 s between fetches (~21/min) |
| 00:01:05 | 00:02:51 | 00:17:30 | 373 | same |

Both ended with a genuine redirect to `/Login/MainPage` in the middle of a window, while the worker
was fetching a page every 2-3 seconds. That rules out an idle timeout (the session was never idle), a
fixed session lifetime (27 minutes versus 16), and a page count per session (532 versus 373). What
fits is a page-view quota per account over a rolling hour of roughly 500-600 views: the second
session died after 373 of its own pages plus about 240 the first session had fetched inside the same
rolling hour. The site is ending the login because the account is reading too fast; this is the
soft form of the throttling the contract's pacing budget exists to stay under.

**F17 — backfill pacing was set above what the site tolerates.** The backfill profile paced
PakistanLawSite at 0.4-1.0 s between fetches with a 10,000-page hourly budget, so the run reached the
site's quota in 15-26 minutes and then needed a human login. Fixed: 6-9 s between fetches (about
380 pages per hour, 9,000 per day, the 20,568-row grid in about 2.5 days) and a 450-page hourly
budget as a backstop. When the budget is reached the run pauses itself and resumes on the next
scheduled dispatch, needing nobody. `cloud/install.sh` migrates the three old values in an existing
`.env`. If the session now survives past the hour, the diagnosis is confirmed and the pace can be
raised step by step (each step measured the same way); if it still ends 15-30 minutes after login
at this pace, the quota theory is wrong and the remaining explanation is a site-side session
lifetime, for which the only remedies are a human login each time or the saved-credentials login
the operator must authorise expressly.

One open point for the operator: the logins at 23:01:15 and 00:01:05 are recorded as made
"by server-login", and the API container's access log shows no dashboard traffic at either time, so
they were made through some other instance of the service against the same database. Two instances
sharing one PakistanLawSite account and one database are not a supported deployment; whatever made
those logins should be identified and, if it also harvests, stopped.

## 11. Running around the clock on two logins (23 September, 01:30 UTC)

The operator's instruction is continuous operation on the two logins the firm holds: if one login
cannot be used, the other is tried. Three further defects stood in the way of that, all fixed here.

**F18 — a bounced slot was never re-checked.** When the site redirected a slot to its login page the
slot went to `NEEDS_HUMAN_LOGIN` and stayed there until a person logged in, whether or not the
session behind it was still alive (a busy-account bounce and a real logout look the same at the
moment they happen). The new `recover-login-slots` Beat task re-opens the stored session after a
15-minute cool-down and loads the search page; if it renders, the slot is ACTIVE again and a paused
source resumes at once. If the site really ended the login, the task signs in again with the
username/password the operator saved for the slot, in the same server-side browser the streamed
human login uses, and stores the new session (the operator authorised this unattended sign-in
expressly on 23 September 2026; credentials stay encrypted at rest and are never logged). A slot
never logged in but holding saved credentials is brought up the same way. A verification page at
sign-in is never solved: the slot waits two hours between attempts and a notification asks for a
human. Failed attempts back off 15, 30, 60 minutes.

**F19 — two shards could land on one login, and overwrote each other's state.** Nothing stopped a
second job from opening a browser on a slot another job was using (the dispatcher re-queued both
shards whenever both slots were ACTIVE, even while one shard still ran), and the two shards wrote the
whole `config_json` back from their own copies, so each overwrote the other's grid cursor and page
counters. Now: every job takes an exclusive Redis lock on its slot (`…:slot<n>`) and a second job
that lands on a held slot skips with `slot_in_use`; the dispatcher starts only the shard whose slot
has no running job (from the heartbeat's `reporter_shard`) and starts nothing beside an unsharded
job; and all config writes are atomic top-level merges (`config_json || patch`), so cursors,
counters and recovery records of one slot never touch the other's.

**F20 — one page budget for two accounts.** The hourly and daily counters were per source, so two
logins would have shared one 450-page budget while the site's quota is per account. Counters are
now per slot (`pacing_slot_<n>`), and `LOGIN_SESSION_CONCURRENCY=2` is the shipped default so both
logins are used in parallel (the installer migrates `1` → `2`).

Expected steady state with both slots logged in: two browsers at about 380 pages per hour each,
some 18,000 pages a day, the 20,568-row grid in about 30 hours, then the frontier; a bounce on one
slot costs that slot 15-60 minutes while the other continues.

**Also (23 September, 01:45 UTC):** the caddy container reported "unhealthy" while serving the
dashboard normally. Its health probe went through the public listener, which redirects plain HTTP
to HTTPS and serves the certificate for the server's IP, not for 127.0.0.1, so the probe could never
pass. It now asks Caddy's loopback admin endpoint whether a configuration is being served.

**F21 — after every deploy the harvest idled for half an hour (23 September, 02:00 UTC).** A
deploy recreates the login-session worker while a job runs; the job's row stayed `running` and
blocked the dispatcher until the 30-minute heartbeat cut-off retired it. The login-session worker
now retires every login-session job still recorded as running when it boots (only that worker runs
them, so any such row is dead), and the next job starts at the next dispatch, resuming at the
committed cursor. The same worker start also drops the Redis session locks those dead jobs held:
they expire only after an hour, and until then every new job skipped as "lock held" (seen at
02:25 UTC, an hour after the 01:25 deploy).
